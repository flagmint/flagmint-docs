## Scheduled releases

- On any flag, open **Schedule** (beside Rollout)
- Choose whether to turn the flag **on** or **off**, then pick when — including the timezone your team works in
- Change your mind anytime: pause, resume, edit, or cancel before it runs
- Flag cards show what’s coming next (for example, *Scheduled · On 7 Oct, 09:00*)
- When the time comes, the dashboard updates on its own — and the change is dispatched to your **edge nodes** (connected SDKs) so apps pick it up without a redeploy

### Pause and resume

You can hold a schedule without throwing away the time you already picked.

- **Pause** — The flip does **not** run at the scheduled time. The flag stays as it is today. The card badge switches to *Paused · …* with the same date and time. Cancel or edit are still available while it’s paused.
- **Resume (time still in the future)** — The schedule is armed again for that same date and time. The badge goes back to *Scheduled · …*, and the on/off change runs when the clock hits that moment.
- **Resume (time already passed)** — Flagmint applies the on/off change **right away**. The pending schedule clears (no leftover “Scheduled” badge for a time that’s already gone), the dashboard updates, and connected SDKs get the change like a normal apply.

Editing the schedule (new time or on/off) works whether it’s scheduled or paused. A paused schedule stays paused until you resume; picking a new future time does not auto-arm it.

Full guide: [Scheduled releases](/concepts/scheduled-releases). Recurring schedules and email/Slack reminders are planned next.

## Usage pot and meters

Plans still have an included monthly allowance. What changed is how we **show** and **count** the work that fills it.

- One **included usage** pot for the billing period — server evaluations, live sessions, observed contexts, and track events each use a credit from that pot
- **Local** `getFlag` in config-sync mode does **not** spend that pot (great for high-volume web/server reads)
- On Plans, early-access orgs see a simple breakdown of what spent the pot — everyone else keeps the classic view until we open it more widely
- Optional **brakes** on sessions, contexts, or track alone (when your plan defines them). With on-demand overage on, the monthly spend cap is what stops you — not a surprise hard block mid-overage
- Approaching or hitting your included limit? Paid orgs get clearer email at **80% / 90% / 100%**, including when limits reset

Full guide: [Usage](/billing/usage).

## Local evaluation (config sync)

Signed rules to the client, evaluate on-device, reconnect with catch-up instead of always re-downloading everything.

- Safer for multi-server Node apps that plug in their own cache (for example Redis) so workers share the same rules across restarts
- Call-site reads can still feed your **Evaluations** charts when analytics is on for that flag — without burning billing credits
- Local `getFlag` does **not** spend from the included usage pot (opening a live session still does)

**Requirements:** Flagmint **API 1.7.0+** and **`flagmint-js-sdk` 2.2.1+** (do not use the incomplete 2.2.0 runtime build). Config sync may still be **gradually enabled** per organization.

Full guide: [JavaScript — Local evaluation](/sdks/nodejs-local-evaluation).

## Config sync (local evaluation)

Opt-in for the JavaScript SDK. The API still supports the classic SSE “evaluated flags” path.

- Handshake may exchange ECDH keys so each connection gets its own signing secret (the secret is never sent on the wire)
- Stream events in config mode: `lease`, `fullConfig`, and `delta` / `deltas` (catch-up when you reconnect)
- `GET /evaluator/v2/flags/config` — fetch a signed snapshot or catch-up without holding a stream open
- Expired lease → fail closed (defaults only; no offline targeting abuse)
- Soft warnings when a rules snapshot is very large (does not hard-fail by default)

**JavaScript SDK (`flagmint-js-sdk` v2.1+; use v2.2.1+ for production Node)**

- Set `configSync: true` to use local evaluation
- Optional local cache of rules across page reloads (or your own Redis / file adapter in Node)
- Optional `debugLog` lines for stream connect / disconnect (for support)

See the [Node.js / JavaScript SDK](/sdks/nodejs).

<Update label="v1.3.0" description="Released August 21, 2026">

## Highlights

Real-time JavaScript evaluation now uses **Server-Sent Events**, and flags can **auto-pause when they cause errors** in production.

## SSE evaluation stream

The JavaScript SDK (v2) no longer uses WebSocket.

- `POST /auth/asl-handshake` — exchange `x-api-key` for a single-use `sessionId` (5 minute TTL, consumed when the stream opens)
- `GET /evaluator/v2/flags/stream` — `text/event-stream` with `connected`, `flags`, `quota_exceeded`, and `error` events; heartbeats are SSE comments
- `POST /evaluator/v2/flags/context` — queue a context change (`202`); flags are pushed on the open stream after a short debounce
- Stream open and context posts count against evaluation quota
- `POST /evaluator/evaluate` remains for one-shot and long-polling clients (deprecated in the API docs)
- Go SDK continues to use WebSocket at `/ws/sdk`

**JavaScript SDK (`flagmint-js-sdk` v2)**

- `transportMode`: `'auto' | 'sse' | 'long-polling'` (`'websocket'` removed)
- Node.js requires `EventSourceImpl` (for example `eventsource`)
- `ready()` always resolves; failures go to `onError` (`ERR_AUTH`, `ERR_RATE_LIMITED`, …)
- Optional same-origin connection sharing in browsers (`shareConnection`)
- Reconnects handshake for a fresh `sessionId` before opening EventSource again

See the [Node.js / JavaScript SDK](/sdks/nodejs) and [evaluation API](/api-reference/evaluate).

## Application errors and guardrails

Feature flags can now measure whether a served variation hurt users — counts only, not crash payloads.

- SDKs report via `trackError()` → `POST /evaluator/events`, attributed to the variation that was served
- Analytics Tracking must be on for that flag; ingest does not use evaluation quota
- Per-environment **guardrails**: error-rate threshold, minimum evaluations, in-app and email notify, auto-pause
- Auto-pause turns the env rollout off, or the flag off if there is no rollout, and **broadcasts to connected SDKs** the same way the inactive/active toggle does
- **QA fire drill** trips the checker immediately with a synthetic burst (does not change Metrics). Rate limited to 5 runs per organization per hour

## Other changes

- New organizations get default **Live** and **Staging** environments on setup
- Deleting a variation detaches it from variant rollouts and rebalances weights
- Deleted flags are no longer evaluated
- API responses include `X-App-Version`

</Update>
