Usage is tracked **per organisation**, not per seat or per project. The included allowance resets with your **billing period** (see Plans in the dashboard for when limits reset).

View current usage under **Settings → Billing**, or via [`GET /billing/usage`](/api-reference/billing/get-current-month-usage-for-organization).

<Note>
  **API v1.7.0+** introduces a unified **included usage** pot and optional meter brakes. Pair local evaluation with **`flagmint-js-sdk` 2.2.1+**. See [JavaScript — Local evaluation](/sdks/nodejs-local-evaluation).
</Note>

## Included usage pot

Plans include a monthly **usage** allowance (credits). These activities each spend **1 credit** from that pot:

| Meter | What it is |
|-------|------------|
| **Server evaluations** | Flagmint computed flags on the server (REST evaluate, mobile WebSocket / server-eval streams) |
| **Sessions** | Live SDK opens — SSE (web/server) or WebSocket (mobile) |
| **Observed contexts** | Context reports used for insights / telemetry |
| **Track events** | Accepted custom `track()` events |
| **Track errors** | Accepted `trackError()` events |

These do **not** spend from the pot:

- **Local** `getFlag` / `getFlags` when the JS SDK runs with `configSync: true` ([local evaluation](/sdks/nodejs-local-evaluation))
- ASL handshake
- SSE heartbeats / WebSocket ping-pong
- Failed requests (4xx / 5xx), login, and dashboard reads

Flag and project **resource** limits (how many flags/projects you can create) are separate and still return **403** at create time.

## Optional meter brakes

Your plan may also define optional caps on sessions, observed contexts, track, or track errors alone. Behaviour:

- **Free**, or paid with overage **off** — hitting a brake can hard-stop that activity (for example stream open / track returns quota exceeded).
- **Paid with on-demand overage on** — the monthly **spend cap** is what stops you; a lower meter brake does not surprise-block you mid-overage.

## When you hit the included limit

| Plan | What you see |
|------|----------------|
| **Free** | Hard stop at the included pot. Cached / local flags may keep serving; new billable activity is throttled (`429` or SSE `quota_exceeded`). |
| **Pro / Growth (overage off)** | Hard stop at the included pot (plus any grace your plan defines). |
| **Pro / Growth (overage on)** | Usage can continue into on-demand blocks; the **spend cap** (if set) is the ceiling. |
| **Custom** | Contract limit; overage terms as agreed |

Paid orgs get clearer email as you approach or hit the pot (**80% / 90% / 100%**), including when limits reset.

The JavaScript SDK surfaces quota as `ERR_RATE_LIMITED` on `onError`. `ready()` still resolves if a snapshot exists. See [Error handling](/sdks/nodejs#error-handling).

<Info>
  Opening a live session still spends a credit even in config-sync mode. Reconnect storms and `updateContext()` on every HTTP request against a singleton client will burn allowance quickly — local `getFlag` will not.
</Info>

## Dashboard

- **Settings → Billing / Plans** — included usage used vs limit
- Early-access orgs may see **What spent the pot** (breakdown by meter). Others keep the classic evaluations view until we open the breakdown more widely.

## Usage API

Admins can read current usage from [`GET /billing/usage`](/api-reference/billing/get-current-month-usage-for-organization).

On API **1.7.0+**, responses may include:

- `usage` — pot used / limit  
- `breakdown` / `meters` — when your org has the usage-wallet UI enabled  
- `features.usageWallet` — whether the dashboard should show the pot breakdown  

`limit` is `null` when that meter is unlimited on the plan.
